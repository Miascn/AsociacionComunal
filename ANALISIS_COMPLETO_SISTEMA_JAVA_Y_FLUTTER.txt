1. RESUMEN EJECUTIVO Y ARQUITECTURA GENERAL DEL ECOSISTEMA
================================================================================

El repositorio "AsociacionComunal" implementa una solución informática integral
para la administración vecinal, finanzas comunitarias, gestión de asambleas,
votaciones democráticas y censo de viviendas para una Asociación Comunal en
El Salvador.

El proyecto está diseñado bajo una arquitectura desacoplada basada en servicios
(API-First / Client-Server Architecture):

+------------------------------------------------------------------------------+
|                             CAPA DE CLIENTES                                 |
|                                                                              |
|  [ Cliente Escritorio JavaFX ]            [ Cliente Móvil Flutter ]          |
|  (Módulo 'frontend' - Java 21)            (Carpeta 'flutter-app' - Dart)     |
|  - Uso: Junta Directiva / Admin           - Uso: Residentes y Miembros       |
|  - UI: FXML, AtlantaFX, MaterialFX        - UI: Material 3 + Glassmorphism   |
|  - Comunicación: REST / JSON              - Comunicación: REST / JSON        |
+-----------------------+----------------------------------+-------------------+
                        |                                  |
                        | HTTP/HTTPS                       | HTTP/HTTPS
                        | Authorization: Bearer JWT        | Authorization: Bearer JWT
                        v                                  v
+------------------------------------------------------------------------------+
|                         CAPA DE SERVICIOS (BACKEND)                          |
|                                                                              |
|  [ Servidor de Aplicación Javalin ] (Módulo 'api')                           |
|  - Javalin 7.2.2 embebido sobre Jetty                                        |
|  - Jackson JSR-310 (Serialización y manejo estricto de fechas ISO-8601)      |
|  - Middlewares: JwtAuthMiddleware, AuthMiddleware, BitacoraService           |
|  - 19 Controladores REST, 19 Servicios de Negocio, 44 DTOs de frontera       |

Estructura de directorios raíz del repositorio:
- `pom.xml`: Reactor Maven que gestiona los submódulos `api` y `frontend`.
- `api/`: Servidor backend REST autónomo.

- `qa-local.properties`: Configuración de conexión del frontend a la API remota.

2. ANÁLISIS DE LA APLICACIÓN JAVA (BACKEND API - MÓDULO `api`)
================================================================================

2.1 Pila Tecnológica y Configuración Central
-------------------------------------------
El módulo `api` es una aplicación Java 21 construida como un micro-servidor sin
la pesadez de frameworks como Spring Boot o Jakarta EE, priorizando velocidad de
arranque, bajo consumo de memoria y simplicidad de mantenimiento.

- Lenguaje: Java 21 (usa Records, Switch Expressions, Pattern Matching, Text Blocks).
- Framework Web: Javalin 7.2.2 (sobre servidor web embebido Jetty).
- Conector de Base de Datos: MySQL Connector/J 8.3.0 (`com.mysql:mysql-connector-j`).
- Procesamiento JSON: Jackson 2.21.3 (`jackson-databind` y `jackson-datatype-jsr310`).
- Seguridad y Tokens: JJWT 0.12.6 (`jjwt-api`, `jjwt-impl`, `jjwt-jackson`).
- Logging: SLF4J 2.0.17 (`slf4j-simple`).
- Testing: JUnit Jupiter 5.14.2.
- Empaquetado: Maven Shade Plugin 3.6.0 (crea un fat JAR ejecutable con Main-Class `sv.asociacion.ApiServer`).

Configuración JSON y Manejo de Fechas (`ApiServer.configurarJson`):
Se registra explícitamente `JavaTimeModule` en el `ObjectMapper` de Jackson y se
deshabilita `SerializationFeature.WRITE_DATES_AS_TIMESTAMPS`. Esto asegura que
tipos como `LocalDate` y `LocalDateTime` viajen en formato estándar ISO-8601
(ej. "2026-09-24T19:40:00") y no como arreglos numéricos, garantizando
interoperabilidad con clientes en JavaFX, Flutter y navegadores web.

Manejo Global de Errores (`ApiServer.configurarManejoErrores`):
- `InvalidFormatException`: Se captura específicamente para devolver respuestas
  HTTP 400 Bad Request detallando exactamente qué campo del JSON fue mal formado.
- `Exception.class`: Captura genérica de cualquier error imprevisto, devolviendo
  HTTP 500 Internal Server Error con un mensaje seguro que no expone trazas de
  pila internas ni credenciales al cliente.


2.2 Arquitectura por Capas y Raíz de Composición
------------------------------------------------
El backend implementa una arquitectura limpia por capas estrictamente
unidireccional:

   [ HTTP Request ]
          │
          ▼
   1. MIDDLEWARE (`sv.asociacion.middleware`)
      - Valida tokens JWT en `/api/*` y secretos de actualización en `/api/updates/*`.
      - Deja atributos en el contexto de Javalin (ej. `idUsuario`).
          │
          ▼
   2. CONTROLADOR (`sv.asociacion.controller`)
      - 19 controladores.
      - Responsabilidad única: Extraer datos de la petición HTTP (path params, body),
        llamar al servicio correspondiente y retornar código HTTP y JSON.
      - Ningún controlador implementa lógica de negocio ni sentencias SQL.
          │
          ▼
   3. SERVICIO (`sv.asociacion.service`)
      - 19 servicios de negocio.
      - Responsabilidad: Reglas de validación, transiciones de estado, orquestación
        y transformación entre Entidades de Dominio y DTOs de salida.
          │
          ▼
   4. DAO (`sv.asociacion.dao`)
      - 17 clases DAO JDBC + 2 clases DAO de archivos `.dat`.
      - Responsabilidad: Ejecución de consultas SQL, mapeo de `ResultSet` a objetos
        y control de transacciones de base de datos.
          │
          ▼
   5. BASE DE DATOS (MySQL) / SISTEMA DE ARCHIVOS

Modelos de Datos Separados (Tres mundos diferentes):
- `domain.entity`: Clases Java que reflejan fielmente las tablas de la BD (usan
  tipos ricos como `LocalDate`, enums de Java como `Miembro.Estado`).
- `domain.dto`: 44 contratos inmutables (Java Records) que definen la entrada y
  salida de la API. Protegen datos sensibles (ej. `Usuario` tiene `claveHash`, pero
  el DTO de respuesta jamás lo expone).
- `models`: Clases que residen exclusivamente en los clientes (JavaFX / Flutter)
  para presentación y enlace de datos.

Raíz de Composición (`ApiServer.java`):
`ApiServer` actúa como la raíz de composición manual del sistema. En su método
`main()`, instancia las dependencias en orden topológico (de abajo hacia arriba):
1. Instancia los DAOs (`new MiembroDAO()`, `new UsuarioDAO()`, etc.).
2. Instancia los Servicios inyectando los DAOs correspondientes.
3. Instancia los Controladores inyectando los Servicios.
4. Mapea las rutas HTTP de Javalin a los métodos de los controladores.
No requiere contenedores pesados ni reflexión; el grafo de dependencias se lee
de forma lineal, transparente y determinista.


2.3 Seguridad y Esquemas de Autenticación
----------------------------------------
El sistema cuenta con un modelo de seguridad híbrido y adaptado a cada tipo de cliente:

A) Autenticación para Panel Administrativo y Escritorio:
   - Endpoint: `POST /api/admin/auth/login`
   - Se valida usuario y contraseña contra la tabla `usuario`.
   - Se emite un token JWT firmado mediante clave simétrica HMAC-SHA configurada
     por `JWT_SECRET` (mínimo 32 caracteres).
   - El token contiene claims con `idUsuario`, nombre de usuario y rol.
   - Duración de expiración: 15 minutos (para mitigar riesgos de sesión robada).

B) Autenticación para Cliente Móvil / Residentes (Sesiones Persistentes):
   - Endpoint: `POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`.
   - Implementado mediante `sv.asociacion.api.auth.AuthService`, `JdbcSessionRepository`
     y `JdbcUserAuthRepository`.
   - Al autenticarse, devuelve:
     * `accessToken`: Token de corta duración para consumo diario de endpoints.
     * `refreshToken`: Token seguro de larga duración almacenado con hash criptográfico
       en la tabla `sesion_usuario`.
   - Soporta cambio forzado de contraseña en primer inicio de sesión mediante
     `POST /api/auth/change-password` (activado cuando un residente es provisto por DUI).

C) Middleware de Validación (`JwtAuthMiddleware`):
   - Se ejecuta mediante `cfg.routes.before("/api/*", ...)`.
   - Examina el encabezado `Authorization: Bearer <token>`.
   - Rutas públicas exentas: `/health`, `/api/admin/auth/login`, `/api/auth/login`,
     `/api/auth/refresh`, endpoints de manifiestos y paquetes de actualización.
   - En caso de token inválido o vencido, interrumpe el flujo inmediatamente con
     HTTP 401 Unauthorized y ejecuta `context.skipRemainingHandlers()`.


2.4 Capa Transversal: Auditoría y Bitácora Automática
-----------------------------------------------------
En `ApiServer.java` (líneas 268-283) se implementa un filtro `after("/api/*")`
que centraliza la auditoría de todo el sistema:
- Monitorea todas las peticiones con verbos `POST`, `PUT`, `PATCH`, `DELETE`.
- Solo si la respuesta tiene código de éxito (2xx), extrae la entidad, la acción,
  el ID del recurso afectado y el `idUsuario` registrado en el contexto por el
  middleware de autenticación.
- Invoca a `bitacoraService.registrar(...)` para persistir la traza en la tabla
  `bitacora`.
- Se excluye automáticamente la ruta `/api/bitacoras` para evitar ciclos infinitos
  de auditoría al consultar el log.
- Ventaja arquitectónica: Ningún controlador ni servicio contiene código repetitivo
  de auditoría; el sistema registra automáticamente cada mutación de datos.

3. CÓMO SE CONECTA LA APLICACIÓN JAVA A LA BASE DE DATOS
================================================================================

3.1 Conector y Tecnología de Enlace
-----------------------------------
La conexión con la base de datos se realiza mediante JDBC estándar puro (Java
Database Connectivity) sin capas de abstracción pesadas (sin Hibernate, JPA ni
MyBatis).

- Driver oficial utilizado: `com.mysql.cj.jdbc.Driver`
- Dependencia Maven: `com.mysql:mysql-connector-j:8.3.0`
- Carga del driver: Se garantiza en un bloque estático de inicialización:
  ```java
  static {
      try {
          Class.forName("com.mysql.cj.jdbc.Driver");
      } catch (ClassNotFoundException exception) {
          throw new IllegalStateException("No se encontró el controlador JDBC de MySQL.", exception);
      }
  }
  ```


3.2 Patrón Singleton: Clase `sv.asociacion.config.DBConnection`
--------------------------------------------------------------
Ubicación del archivo:
`api/src/main/java/sv/asociacion/config/DBConnection.java`

`DBConnection` está implementado como un Singleton seguro para hilos (thread-safe):
- Constructor privado `private DBConnection() { }`.
- Método de acceso global sincronizado:
  ```java
  public static synchronized DBConnection getInstance() {
      if (instance == null) {
          instance = new DBConnection();
      }
      return instance;
  }
  ```
- Método para obtener conexiones:
  ```java
  public Connection getConnection() throws SQLException {
      return DriverManager.getConnection(DB_URL, DB_USER, DB_PASSWORD);
  }
  ```
Cada llamada a `getConnection()` obtiene una conexión activa directamente del
`DriverManager`. En los DAOs se utiliza siempre la estructura `try-with-resources`:
```java
try (Connection conn = DBConnection.getInstance().getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql)) {
    // Uso de la conexión
} // Al cerrarse el try, la conexión y el statement se cierran automáticamente
```


3.3 Resolución de Configuración y Credenciales en Cascada
---------------------------------------------------------
Para permitir despliegues en servidores de producción, entornos de prueba y
entornos locales de desarrollo, `DBConnection` implementa una estrategia de
resolución jerárquica en cascada:

Prioridad 1: Variables de Entorno del Sistema Operativo
- `DB_HOST`: Nombre de host o IP del servidor MySQL (ej. `localhost` o `100.64.210.47`).
- `DB_PORT`: Puerto de escucha de MySQL (por defecto: `3306`).
- `DB_NAME`: Nombre de la base de datos (por defecto: `asociacion_comunal`).
- `DB_USER`: Usuario con permisos (obligatorio).
- `DB_PASSWORD`: Contraseña del usuario (obligatorio).
- `DB_PARAMETERS`: Opciones adicionales de URL JDBC.
- `DB_CONFIG_FILE`: Ruta explícita a un archivo de propiedades personalizado.

Prioridad 2: Propiedades del Sistema de Java (`System.getProperty`)
- Si no está en variable de entorno, busca propiedades pasadas con la bandera `-D`
  al iniciar la máquina virtual Java.

Prioridad 3: Archivo de Propiedades Local (`database-local.properties`)
- Si no se encuentra en el entorno, `DBConnection.configuredPropertiesPath()` busca
  un archivo llamado `database-local.properties` en el directorio actual (`.`) o en
  el directorio padre (`..`).
- Ejemplo del archivo activo detectado en el proyecto:
  ```properties
  db.host=100.64.210.47
  db.port=3306
  ```

3.4 Cadena de Conexión JDBC y Parámetros
----------------------------------------
La URL final generada por `DBConnection.buildUrl()` tiene la forma:
`jdbc:mysql://{host}:{port}/{database}?{parameters}`

Parámetros estándar configurados:
- `serverTimezone=America/El_Salvador`: Garantiza que las fechas y horas registradas
  por MySQL coincidan con la hora oficial salvadoreña (UTC-6) sin desfases por
  zonas horarias del servidor anfitrión.
- `useUnicode=true&characterEncoding=UTF-8`: Asegura el soporte completo para
  tildes, caracteres especiales y emojis sin corrupción de texto.
- `connectTimeout=5000`: Timeout de conexión de 5 segundos para no dejar hilos
  bloqueados si el servidor de base de datos no está disponible.
- `socketTimeout=10000`: Timeout de lectura de socket de 10 segundos para abortar
  consultas congeladas.

3.6 Manejo de Transacciones ACID en la Capa DAO
-----------------------------------------------
Las transacciones no se delegan a anotaciones mágicas ni se suben a la capa de
negocio. Se controlan explícitamente a nivel de JDBC dentro del DAO para garantizar
atomicidad física.

Ejemplo crítico: `MiembroDAO.changeEstado(Integer id, Miembro.Estado estado)`:
Cuando se da de baja a un miembro, deben actualizarse dos tablas obligatoriamente:
1) `UPDATE miembro SET estado = ? WHERE id_miembro = ?`
2) `UPDATE usuario SET estado = ? WHERE id_miembro = ?`

Si se actualizara el miembro pero fallara el usuario, quedaría una persona
inactiva pero cuya cuenta seguiría pudiendo ingresar al sistema.

Implementación real en `MiembroDAO.java:131`:
```java
try (Connection conn = DBConnection.getInstance().getConnection()) {
    conn.setAutoCommit(false); // Inicia transacción atómica
    try (PreparedStatement member = conn.prepareStatement(memberSql);
         PreparedStatement user = conn.prepareStatement(userSql)) {
        
        member.setString(1, estado.name());
        member.setInt(2, id);
        boolean changed = member.executeUpdate() > 0;
        if (!changed) {
            conn.rollback();
            return false;
        }

        user.setString(1, estado == Miembro.Estado.ACTIVO ? "ACTIVO" : "INACTIVO");
        user.setInt(2, id);
        user.executeUpdate();

        conn.commit(); // Éxito: confirma ambas tablas
        return true;
    } catch (SQLException exception) {
        conn.rollback(); // Error: revierte ambas tablas de inmediato
        throw exception;
    } finally {
        conn.setAutoCommit(true);
    }
}
```


3.7 Persistencia Polimórfica: Contrato `DAO<T, ID>`
---------------------------------------------------
El sistema cuenta con un diseño avanzado en el paquete `sv.asociacion.dao` a través
de la interfaz genérica `DAO<T, ID>`:
```java
public interface DAO<T, ID> {
    Optional<T> findById(ID id);
    List<T> findAll();
    T save(T entity);
    T update(T entity);
    boolean delete(ID id);
}
```

Existen dos familias de persistencia que implementan este contrato:
1. Familia JDBC / MySQL:
   - `MiembroDAO`, `UsuarioDAO`, `ProyectoDAO`, etc.
   - Ejecutan SQL directo contra MySQL.
2. Familia Archivo `.dat` (Avance 2):
   - `AbstractArchivoDAO<T extends Serializable, ID>` y `MiembroArchivoDAO`.
   - Utiliza serialización nativa de objetos Java (`ObjectInputStream` / `ObjectOutputStream`)
     guardando los registros en archivos binarios planos (ej. `miembros.dat`).
   - Diseñado para escenarios donde el local comunal no tiene conexión a la red
     y requiere autonomía local o para pruebas unitarias sin dependencias externas.
   - El servicio `CensoMiembrosService` recibe el contrato `DAO<Miembro, Integer>`,
     lo que significa que puede operar de forma 100% intercambiable contra MySQL
     o contra el archivo binario sin cambiar una sola línea de código en la capa de negocio.

4.2 Desacoplamiento Arquitectónico: ¿El frontend accede a la BD?
----------------------------------------------------------------
REGLA ARQUITECTÓNICA VERIFICADA: EL FRONTEND NO TIENE ACCESO A LA BASE DE DATOS.

Al realizar una búsqueda rigurosa en el código fuente del frontend:
`grep -rl "java.sql|DBConnection|DriverManager" frontend/src/main/java`
Resultado: EXACTAMENTE 0 ARCHIVOS.

El cliente de escritorio desconoce por completo las credenciales de MySQL (`DB_USER`,
`DB_PASSWORD`), la IP del servidor de datos y la existencia de sentencias SQL.
Toda la información viaja estrictamente como peticiones HTTP en formato JSON contra
la API central.

Razones clave de esta decisión:
1. Seguridad: Si el cliente de escritorio incluyera credenciales de MySQL, cualquier
   usuario podría descompilar el software y obtener acceso root/completo a la base de datos.
2. Centralización de Reglas: Las validaciones de negocio (ej. "solo miembros activos votan",
   "voto secreto único", "un cargo por miembro") viven en la API y son compartidas
   idénticamente con la aplicación Flutter.
3. Tokens efímeros: El cliente solo almacena su token JWT en memoria mediante
   `security.SessionManager`, el cual expira tras un periodo de inactividad.


4.3 Flujo de Interacción y Comunicación Cliente-Servidor
-------------------------------------------------------
Para garantizar que la interfaz gráfica permanezca fluida y no se congele durante
las llamadas de red, los controladores de JavaFX utilizan tareas en segundo plano
mediante `javafx.concurrent.Task`:

Ejemplo de flujo (`MiembroController.java`):
1. El usuario hace clic en el módulo de miembros en el menú lateral.
2. El controlador crea una `Task<List<MiembroModel>>` y la ejecuta en un hilo daemon:
   `new Thread(task, "cargar-miembros-api").start();`
3. La tarea invoca a `new MiembroApiClient().findAll()`.
4. `MiembroApiClient` prepara la petición HTTPS con el token de `SessionManager.requireToken()`.
5. Recibe el JSON de la API (`MiembroResponse[]`), lo deserializa con Jackson y
   lo mapea a `MiembroModel` (objetos observables de JavaFX).
6. En el evento `task.setOnSucceeded(...)` (que se ejecuta de vuelta en el hilo de
   JavaFX Application Thread), se actualiza el `TableView` y se ocultan los indicadores
   de carga.

5.4 Capa de Red y Servicios (ApiClient & Auto-Refresh)
------------------------------------------------------
En `flutter-app/lib/data/services/api_client.dart` se implementa un cliente de red
de grado de producción:

- URL Base: Configurada en `ApiConstants.baseUrl` (`https://asociacion-comunal.miascn.org`).
- Encabezados automáticos:
  * `Content-Type: application/json`
  * `Accept: application/json`
  * `User-Agent: AsociacionComunalApp/1.0 (Android/Flutter)`
  * `ngrok-skip-browser-warning: asociacion-flutter`
- Mecanismo transparente de Auto-Refresh de Tokens:
  Si una petición devuelve código HTTP 401 Unauthorized, `ApiClient` no cierra la
  sesión inmediatamente:
  1. Intercepta la respuesta en `_sendWithAutoRefresh`.
  2. Lee el `refreshToken` almacenado de forma segura en `SessionStorageService`.
  3. Ejecuta una llamada en segundo plano a `POST /api/auth/refresh`.
  4. Si el servidor emite un nuevo `accessToken`, lo actualiza en el almacenamiento
     seguro y vuelve a reintentar la petición original sin que el usuario note ninguna
     interrupción.
  5. Solo si el `refreshToken` también expiró o fue revocado, dispara la devolución de
     llamada `onSessionExpired` que redirige automáticamente al usuario a `LoginView`.

7. CONCLUSIONES Y RECOMENDACIONES TÉCNICAS
================================================================================

1. Arquitectura Robusta y Desacoplada:
   El proyecto Asociación Comunal exhibe una arquitectura modular de estándar
   profesional. La separación entre el servidor Javalin, el cliente de escritorio
   JavaFX y la app móvil Flutter garantiza que la lógica de negocio esté blindada
   en el servidor, impidiendo inconsistencias de datos o filtración de credenciales.

2. Integridad de la Base de Datos:
   La conexión a MySQL está optimizada con un Singleton limpio (`DBConnection`),
   resolución elástica de variables de entorno y transacciones manuales atómicas
   (ACID) en los DAOs que protegen la coherencia de datos entre tablas vinculadas.
   El esquema relacional cuenta con restricciones de unicidad e integridad foránea
   sólidas.

3. Persistencia Polimórfica (Avance 2):
   El diseño del contrato `DAO<T, ID>` y su implementación dual (MySQL vía JDBC y
   archivos serializados `.dat`) representa una solución de alto mérito técnico,
   permitiendo conmutar la fuente de datos para escenarios sin conexión sin alterar
   la capa de servicios ni controladores.

4. Calidad del Cliente Flutter:
   La aplicación Flutter no es un simple visor; cuenta con una arquitectura completa
   MVVM + Repository, gestión inteligente de expiración de sesiones mediante
   auto-refresh transparente de tokens, almacenamiento en bóveda segura y una
   interfaz moderna Glassmorphism adaptada a residentes.

5. Recomendación de Mantenimiento Futuro:
   - En el backend, migrar la dependencia directa detectada en `VotoController`
     (que accede directamente a `UsuarioDAO`) hacia `VotoService` para preservar al
     100% la pureza de la regla de no invocar DAOs desde controladores.
   - En despliegues masivos de alta concurrencia, considerar incorporar un pool de
     conexiones JDBC como HikariCP sobre `DBConnection` para reutilizar conexiones
     activas de manera más eficiente.
